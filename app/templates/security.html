Security model

What QRShare actually protects, and what it does not.

The QR code is not the security boundary. It is a convenient way to move a URL from a screen to a camera. Anyone who can photograph the code has the link, exactly as if you had emailed it. Protection comes from what sits behind the link.

Encryption at rest

Every upload gets its own random 256-bit key and is encrypted with AES-256-GCM before anything is written to disk. That per-file key is then encrypted with a server master key that lives in the environment, never in the database and never in source control.

The file body is stored as a sequence of independently authenticated 1 MiB frames rather than one giant sealed blob. Each frame carries its own index in the authenticated data, so frames cannot be reordered, duplicated or dropped, and the last frame is marked as final so the file cannot be silently truncated. Every frame is verified before its bytes are handed to you.

What protects a link

The token alone is a bearer credential. Four things make it safe to hand around:

  • Unpredictability. Tokens come from secrets.token_urlsafe(32) — 256 bits of OS entropy. No counters, no timestamps, no hashes of the filename.
  • Expiry. Between 1 minute and {{ max_expiry }} minutes, default {{ default_expiry }}. Checked on every single access.
  • Optional password. Argon2id, verified server-side. The check runs even when no password is set, so response timing does not reveal which shares are protected.
  • One-time consumption. The link is claimed with a conditional UPDATE … WHERE used = 0 before any byte is streamed, so concurrent requests cannot both be served.

Other measures

Rate limiting

Separate budgets for uploads, password attempts, downloads and status polls.

Storage isolation

Blobs live outside the web root under random names. Original filenames are metadata only and never form a path.

Audit log

Views, downloads, failed passwords and deletions are recorded. Passwords and keys never are.

Hardened responses

CSP with no inline scripts, CSRF tokens, nosniff, frame denial, and downloads forced to attachment.

Honest limitations

Things a viva examiner should hear stated plainly:

  • This is not end-to-end encryption. The server holds the master key, so a compromised server can read files. True E2EE would need the key to live in the URL fragment and never reach the server.
  • Transport security is the deployment's job. Running python run.py serves plain HTTP on localhost. HSTS stays off unless TLS is genuinely configured, because promising HTTPS you do not have locks users out.
  • An interrupted one-time download still counts as used. Claiming the link before streaming is what makes the race impossible; failing closed is the right direction for a link that promises single use.
  • Default rate limiting is per process. The in-memory counter is fine for one worker; a multi-worker deployment needs a shared store.
  • No malware scanning. Uploads are treated as untrusted bytes, always served as an attachment, never executed — but they are not inspected.
